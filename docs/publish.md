# Процесс публикации контента

## Общая схема

```txt
src/{posts,projects,weekly}/*.md  →  prepare-post.js  →  .post-meta.json  →  publish.js  →  Telegram/Discord
                                                                                                ↓
                                                                                          posts.yaml (ветка posts_db)
```

## Типы контента

| Тип          | Папка           | Шаблон                                                |
| ------------ | --------------- | ----------------------------------------------------- |
| Посты        | `src/posts/`    | "Выложен новый пост: {title}\n\n{excerpt}\n\nссылка"  |
| Проекты      | `src/projects/` | "Добавлен проект: {title}\n\n{description}\n\nссылка" |
| Итоги недели | `src/weekly/`   | "Итоги недели\n\n{excerpt}\n\nссылка"                 |

Шаблоны хранятся в `scripts/templates.json`.

## Триггер

Workflow запускается при пуше в ветку `main`, если изменились файлы в
`src/posts/`, `src/projects/` или `src/weekly/`. Также доступен ручной запуск
через `workflow_dispatch`.

## Пошаговый процесс

### 1. Подготовка окружения

- Checkout репозитория с полной историей (нужна ветка `posts_db`)
- Установка Node.js и зависимостей
- Загрузка `posts.yaml` из ветки `posts_db` в корень рабочей директории

### 2. Подготовка контента (`prepare-post.js`)

**Вход:** список файлов из env var `FILES` — пути через пробел.

**Алгоритм:**

1. Парсинг строки файлов из переменной окружения `FILES`
2. Фильтрация — оставить только `.md` файлы из `src/posts/`, `src/projects/`,
   `src/weekly/`
3. Определение типа контента по пути к файлу
4. Загрузка шаблонов из `scripts/templates.json`
5. Валидация: 0 файлов → тихий выход (код 0)
6. Цикл по каждому файлу:
   - Чтение markdown-файла
   - Парсинг YAML-фронтматтера (между `---`)
   - Для постов: поиск `<!--more-->` → обрезка контента
   - Для проектов: используется `description` из фронтматтера
   - Для итогов недели: поиск `<!--more-->` или `excerpt`
   - Применение шаблона из `templates.json` с подстановкой переменных
7. Сохранение массива метаданных в `.post-meta.json` (включает `socialText` —
   готовое сообщение)

**Выход:** `.post-meta.json` (массив с `socialText`)

### 3. Публикация (`publish.js`)

**Вход:** `.post-meta.json` (массив) + `posts.yaml` + секреты API.

**Алгоритм:**

1. Чтение массива метаданных из `.post-meta.json`
2. Загрузка `posts.yaml`
3. Цикл по каждому элементу:
   - Чтение `socialText` из метаданных (уже отформатированное сообщение)
   - Проверка наличия slug в `posts.yaml`:
     - **Новый контент** (slug отсутствует):
       - Отправка текста в Telegram → получение `message_id`
       - Отправка текста в Discord → получение `id` сообщения
     - **Существующий** (slug найден):
       - Редактирование сообщения в Telegram по сохранённому `message_id`
       - Редактирование сообщения в Discord по сохранённому `id`
       - Если редактирование не удалось → лог ошибки, продолжение
   - Запись message IDs в `posts.yaml`
   - Если элементов больше одного → задержка 1с между отправками (rate limit)
4. Выход с кодом 0

**Выход:** обновлённый `posts.yaml` на диске + отправленные/отредактированные
сообщения

### 4. Сохранение базы данных

- Если предыдущие шаги не упали → коммит `posts.yaml` в ветку `posts_db`
- Если упали → `if: always()` в workflow всё равно пытается сохранить (чтобы не
  потерять данные при частичной отправке)
- Используется бот `github-actions[bot]` для коммита
- Сообщение коммита: `Update posts database [skip ci]` (чтобы не зациклить
  workflow)

## Формат `posts.yaml`

```yaml
posts:
  slug-поста:
    telegram: 123456
    discord: 789012
projects:
  slug-проекта:
    telegram: 234567
    discord: 890123
weekly:
  2026-06-28:
    telegram: 345678
    discord: 901234
```

- Ключ первого уровня — тип контента (`posts`, `projects`, `weekly`)
- Ключ второго уровня — slug (имя файла без `.md`)
- `telegram` — ID сообщения в Telegram (число)
- `discord` — ID сообщения в Discord (строка)
- Slug могут совпадать между типами (например, пост и проект с одинаковым
  именем)

## Формат `<!--more-->`

Тег `<!--more-->` разделяет пост на две части:

- **До тега** — краткое содержание для соцсетей (excerpt)
- **После тега** — основной контент (не отправляется в соцсети)

Пример:

```markdown
---
title: Why I Moved Away from Tailwind
date: 2026.06.28
excerpt: Short summary for feeds
tag: tailwind css
---

Введение и краткое описание проблемы. Зачем это важно.

<!--more-->

Основная часть статьи с деталями, примерами кода и т.д.
```

В соцсети уйдёт только текст до `<!--more-->` + ссылка на сайт.

## Ограничения

- При нескольких постах — задержка 1с между отправками (rate limit
  Telegram/Discord)
- Telegram: `parse_mode: Markdown` — контент должен быть совместим с Markdown
  Telegram
- Discord: простой текст без форматирования
- Редактирование ограничено платформами: Telegram — 48 часов, Discord —
  бессрочно

## Локальное использование

Оба скрипта можно запускать локально:

```bash
# Пост
FILES='src/posts/my-post.md' npx tsx scripts/prepare-post.ts

# Проект
FILES='src/projects/my-project.md' npx tsx scripts/prepare-post.ts

# Итоги недели
FILES='src/weekly/2026-06-28.md' npx tsx scripts/prepare-post.ts

# Несколько файлов разных типов (через пробел)
FILES='src/posts/post.md src/projects/project.md' npx tsx scripts/prepare-post.ts

# Публикация (нужны токены в .env.publish)
npx tsx scripts/publish.ts
```
