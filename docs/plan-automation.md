# Автоматизация: проекты и weekly

> Статус: на ревью. Один из трёх планов: дизайн, модель контента, автоматизация.
> Здесь — манифест проектов и два скрипта: синхронизация описаний проектов из
> README и автогенерация weekly-отчётов из git-логов. Манифест с ручными путями;
> старт с нуля и двуязычность — в плане контент-модели. Контент в
> `src/content/*`, каждый элемент — папка с `index.*.md` (см. план
> контент-модели); скрипты пишут файлы по новой структуре.

## Решено по итогам ревью

Открытые вопросы из прошлой версии закрыты:

1. **Описание из README** — первый содержательный абзац (текст, не список и не
   код) сразу после верхнего заголовка файла. Если найти не удалось — `warn`, и
   проект остаётся `raw`/`need_review` без автоописания.
2. **`need_review` на витрине** — метка только в dev-режиме (как у черновиков),
   в production не выводится. Основной канал — отчёт `sync:projects` и
   `git diff`.
3. **Номера коммитов / ссылки в weekly** — в MVP нет; человекочитаемый текст +
   опциональные числа статистики в `excerpt`. Ссылки добавим на этапе 2 вместе с
   AI-рендером.
4. **Неделя без активности** — файл не создаётся, отчёт и пост не появляются.
5. **Источники weekly** — git-логи (детерминированно, оффлайн) + опционально
   локальный `CHANGELOG.md`, если есть в проекте. `gh releases` — этап 2 (нужна
   сеть/токен).

Вслед за решением модели контента убранное поле `type` у проектов исключается и
здесь — из манифеста и из генерируемых файлов. Все типы контента двуязычны:
скрипты пишут пару `index.ru.md` + `index.en.md` (en — копия-заглушка с
`needs_translation: true`) в папке элемента. Наполнение переводов (в том числе
AI-рендер) — этап 2; наличие пары — сразу.

## Общая схема

```txt
projects.yaml (манифест: пути к проектам + витринные поля)
   │
   ├─→ sync-projects.ts  → src/content/projects/<slug>/index.{ru,en}.md
   └─→ gen-weekly.ts     → src/content/weekly/<дата-понедельника>/index.{ru,en}.md
```

Манифест — единственное место, где пользователь описывает состав проектов. Оба
скрипта его читают. Проекты: автоматическая генерация описания с ручной
вычиткой. Weekly: полностью автоматические, руками не создаются.

## Манифест `projects.yaml` (в корне сайта)

```yaml
projects:
  - slug: now-playing
    path: ../+streaming/now_playing # путь к локальному репозиторию
    repo: https://github.com/Ku6epXBOCTuK/now_playing
    demo: https://ku6epxboctuk.github.io/now_playing # опционально
    image: images/now-playing.jpg # относительно src/content/projects/<slug>/
  - slug: git-overhooks
    path: C:/code/git-overhooks # абсолютный путь — тоже ок
    repo: https://github.com/Ku6epXBOCTuK/git-overhooks
```

- `path` — единственное обязательное поле; всё остальное опционально.
- **Пути указываются вручную и могут быть любыми**: абсолютный путь на любом
  диске (`D:\code\my-project`), путь в домашней папке, относительный (считается
  от корня сайта, например `../+streaming/now_playing`). Соседство с папкой
  сайта не предполагается и не проверяется.
- `slug` — если не указан, берётся из имени папки проекта; определяет имя папки
  элемента `src/content/projects/<slug>/`.
- `title`, `subtitle`, `tags`, `repo`, `demo`, `image` — витринные поля;
  задаются здесь и переносятся скриптом в файл проекта. Витринные поля `icon`
  (эмодзи/символ, по умолчанию `✦`) и `color` (`coral` / `periwinkle` / `sky`,
  по умолчанию `coral`) — тоже отсюда: иконка и акцент карточки проекта на
  витрине (см. план дизайна).

## Скрипт синхронизации проектов (`sync-projects.ts`, `npm run sync:projects`)

### Алгоритм генерации описания проекта

1. Читает `projects.yaml`.
2. Для каждого проекта:
   - разрешает путь (относительный — от корня сайта); если не существует (проект
     не склонирован) — `warn` и переход к следующему;
   - ищет README (регистронезависимо: `README.md` / `readme.md`); если нет —
     `warn` и пропуск;
   - извлекает описание — первый содержательный абзац после заголовка;
   - сравнивает README с прошлой копией
     `src/content/projects/_readmes/<slug>.md`;
   - копирует свежий README в `src/content/projects/_readmes/<slug>.md`;
   - обновляет `src/content/projects/<slug>/index.ru.md` по правилам статусов
     (ниже); при первом запуске создаёт и `index.en.md` — копию-заглушку с
     `needs_translation: true`; существующий en-файл скрипт не перезаписывает
     (перевод — ручная или AI-работа).
3. Печатает отчёт: создано / обновлено / `need_review` / пропущено.

Папка `_readmes` не попадает в контент: glob элементов ведётся по
`*/index.*.md`, а префикс `_` в имени не даёт сборке подхватить её как элемент.

### Статусы проекта

| Статус        | Значение                                            |
| ------------- | --------------------------------------------------- |
| `raw`         | скрипт только что скопировал README, описание сырое |
| `ready`       | описание переписано вручную                         |
| `need_review` | README обновился, ручное описание могло устареть    |

Переходы:

- новый проект → `raw`, `description` = абзац из README;
- `raw`, README изменился → остаётся `raw`, `description` обновляется;
- `ready`, README изменился → `need_review`, `description` **не трогаем**
  (сохраняем ручной труд);
- пользователь переписал описание → сам ставит `ready` (поле `status` в
  frontmatter, удобно во Frontmatter CMS).

Скрипт владеет только полями `description`, `status`, `synced_at` — остальные
(`title`, `subtitle`, `tags`, `image`) не перезаписывает. `repo`/`demo`
переносятся из манифеста при изменении (манифест — источник правды, расхождения
подсвечиваются в отчёте).

### Git-интеграция

Копии README коммитятся в репозиторий сайта:

- `git diff src/content/projects/_readmes/` показывает, что именно поменялось в
  README каждого проекта;
- `git diff src/content/projects/` показывает изменение описаний;
- пуш автоматически запускает workflow публикации, если поменялись файлы в
  `src/content/projects/**` (работает через обновлённые пути триггеров).

### Пример сгенерированного файла

`src/content/projects/now-playing/index.ru.md`:

```markdown
---
title: now-playing
subtitle: obs browser source
description:
  obs browser source widget that displays the currently playing track.
tags:
  - html
repo: https://github.com/Ku6epXBOCTuK/now_playing
demo: https://ku6epxboctuk.github.io/now_playing
image: images/now-playing.jpg
status: raw
synced_at: 2026-09-08
---

## now-playing

obs browser source widget that displays the currently playing track. ...

<!-- дальше — полная копия README, только для просмотра, на сайт не идёт -->
```

На сайт идёт только `description` из frontmatter — как и сейчас. Тело файла —
справочная копия README. Рядом лежит `index.en.md` — копия-заглушка с
`needs_translation: true` (тело «translation in progress.»).

### Крайние случаи

- проект не склонирован → warn + пропуск (статус и описание не меняются);
- нет README → warn + пропуск;
- проект удалён из манифеста → файлы элемента остаются (не удаляем
  автоматически, чистится вручную);
- переименование slug → считается новым проектом (старая папка остаётся);
- несколько README (README.md + README_ru.md) → берём основной `README.md`.

## Скрипт weekly-отчётов (`gen-weekly.ts`, `npm run gen:weekly`)

### Алгоритм weekly-отчетов

1. Читает `projects.yaml` — список проектов с путями (любые пути, абсолютные или
   относительные).
2. Определяет период: текущая неделя (понедельник–воскресенье) или неделя,
   указанная явно: `npm run gen:weekly -- --week 2026-W36`.
3. Для каждого проекта:
   - проверяет, что путь существует (нет — warn, пропуск);
   - `git log --since --until` — коммиты за период;
   - фильтрует шум: merge-коммиты, `[skip ci]`, bump/version-коммиты;
   - группирует по conventional-commits типам: feat / fix / docs / refactor /
     chore / прочее (cocogitto уже используется — префиксы нормализованы);
   - опционально: читает CHANGELOG.md, если есть, и берёт записи за период;
   - считает статистику: коммиты, файлы, +/− строки (числа — для excerpt).
4. Собирает отчёт из блоков по проектам (только проекты, где была активность).
5. Генерирует пару файлов в `src/content/weekly/<дата-понедельника>/` (дата —
   понедельник недели, ISO `YYYY-MM-DD`): `index.ru.md` — основной язык,
   `index.en.md` — копия-заглушка с `needs_translation: true` (содержательный
   перевод — этап 2). Frontmatter: `generated: true`, `generated_at`; body —
   человекочитаемый лог по проектам (обычный markdown; сайт рендерит как есть,
   `excerpt` уходит в соцсети через существующий шаблон).
6. Печатает сводку: проектов с активностью, коммитов, файл создан/обновлён.

### Вид генерируемого файла

`src/content/weekly/2026-09-07/index.ru.md`:

```markdown
---
title: weekly 2026-W37
date: 2026-09-07
excerpt: 4 проекта, 23 коммита. now-playing: v1.2, git-overhooks: новый hooks api.
generated: true
generated_at: 2026-09-08T10:00:00Z
---

## now-playing

- feat(overlay): blur behind panel
- fix(timer): timezone drift on resume

## git-overhooks

- feat: hooks api v2
- docs: readme examples

## итого

23 коммита в 4 проектах.
```

### Повторный запуск и режимы

- Запуск за ту же неделю → файл перезаписывается целиком (источник истины — git,
  а не файл). Уже отправленное в соцсети сообщение можно поправить — механизм
  редактирования в `publish.ts` существует.
- `npm run gen:weekly` — текущая неделя, запись файла.
- `--week 2026-W36` — конкретная неделя (догенерировать пропущенное).
- `--check` — только отчёт в консоль, без записи.

### Запуск

На старте — локальный запуск в конце недели: `npm run gen:weekly`, просмотр,
коммит вместе с остальной работой. Пуш weekly-файла → существующий workflow
отправляет excerpt в Telegram/Discord. Scheduled GitHub Actions (cron в
воскресенье) — отдельное решение на потом: требует доступности всех репозиториев
с CI (тот же аккаунт GitHub — достижимо через checkout Ku6epXBOCTuK/\*).

### Задел под AI (этап 2, не сейчас)

Скрипт строится из двух фаз с явной границей:

- **Фаза «сбор» (детерминированная):** git-логи → структура данных `WeeklyData`
  (проекты, коммиты по типам, статистика). Отладка: вывод в консоль/JSON.
- **Фаза «рендер» (заменяемая):** `WeeklyData` → markdown-отчёт. Сейчас —
  шаблон. Позже — нейронка: тот же `WeeklyData` → промпт → связный текст «что
  происходило на этой неделе» + сгенерированный `excerpt` вместо сухих логов.
  Интерфейс — одна функция, подключение AI не потребует переписывания сбора.

### Гарантии скрипта

- не ходит в сеть (только локальные git-команды и файлы);
- проекты без активности за период не попадают в отчёт;
- проекты с несуществующим путём — warn и пропуск;
- повторный запуск безопасен (перезапись того же файла).

## Изменения в кодовой базе

- `projects.yaml` — манифест (заполняется с нуля по мере добавления проектов в
  работу).
- `scripts/sync-projects.ts`, `scripts/gen-weekly.ts` — скрипты (js-yaml уже в
  зависимостях, git — через child_process). Пишут пару `index.ru.md` +
  `index.en.md` (заглушка) в папку элемента (`src/content/projects/<slug>/`,
  `src/content/weekly/<дата>/`).
- `package.json` — скрипты `sync:projects`, `gen:weekly`.
- `frontmatter.json` — для project поле `status` (choices:
  raw/ready/need_review); для weekly поля `generated`/`generated_at` (только
  просмотр); `needs_translation` — во всех четырёх схемах.
- `scripts/lint-content.ts` — предупреждение (не ошибка) для
  `status: need_review`.
- `src/content/weekly/` — наполняется автоматически (`.gitkeep` удалить при
  первом отчёте).
- `.github/workflows/publish.yml` — пути триггеров на `src/content/**`.
- `docs/automation.md` — чеклист: как запускать, как читать отчёты.

## Развитие плана

Открытые вопросы из прошлой ревизии закрыты — список решений в блоке «Решено по
итогам ревью» в начале документа. Остальные детали: перенос `type`/статусов — в
плане модели контента и дизайна; содержимое переводов генерируемых типов
(projects, weekly) — этап 2 вместе с AI-рендером (файлы-пары создаются сразу).
