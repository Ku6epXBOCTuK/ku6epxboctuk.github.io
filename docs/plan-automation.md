# Автоматизация: проекты и weekly

> План реализации. Манифест проектов в корне сайта плюс пять скриптов: создание
> проекта из GitHub-ссылки, линтер манифеста, синхронизация тела файлов из
> README, автогенерация weekly-отчётов из git-логов, публикация в соцсети по
> селектору. Контент двуязычный: каждый элемент — папка с `index.ru.md` и
> `index.en.md`. Скрипты создают пару файлов сразу; содержательный перевод en —
> этап 2 (раздел 9).

## 1. Манифест `projects.yaml`

Файл в корне сайта — источник правды о составе проектов. Его читают все скрипты,
дописывает только `c:new project`.

```yaml
projects:
  - path: ../+streaming/now_playing # путь к локальному клону
    repo: https://github.com/Ku6epXBOCTuK/now_playing
    homepage: https://ku6epxboctuk.github.io/now_playing
    image: images/now-playing.jpg # относительно src/content/projects/<slug>/
  - path: C:/code/git-overhooks # абсолютный путь — тоже ок
    repo: https://github.com/Ku6epXBOCTuK/git-overhooks
  - slug: my-site-2026-final # опционально: переопределение имени папки
    repo: https://github.com/Ku6epXBOCTuK/my-site
  - repo: https://github.com/Ku6epXBOCTuK/cat-signal
    frozen: true
```

### Поля

| Поле                                                     | Статус                    | Значение                                                                                                                         |
| -------------------------------------------------------- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `repo`                                                   | обязательное              | URL GitHub-репозитория                                                                                                           |
| `path`                                                   | обязательное без `frozen` | путь к локальному клону: абсолютный или относительный от корня сайта; соседство с сайтом не предполагается                       |
| `frozen`                                                 | опциональное              | `true` — проект готов или заброшен, не ведётся; в этом случае `path` не ставится                                                 |
| `slug`                                                   | опциональное              | переопределение имени папки; по умолчанию — имя репо с дефисами (`focus_garden` → `focus-garden`)                                |
| `title`                                                  | опциональное              | по умолчанию — имя репо с дефисами                                                                                               |
| `homepage`, `image`, `subtitle`, `tags`, `icon`, `color` | опциональные              | витринные поля, переносятся в файлы проекта; `icon` по умолчанию `✦`; `color` — `coral`/`periwinkle`/`sky`, по умолчанию `coral` |

### Правила записи

- У каждой записи либо существующий `path`, либо `frozen: true` — третьего
  состояния нет. Запись без `path` и без `frozen` — ошибка линтера: напоминание
  склонировать проект или заморозить его.
- **`frozen: true`** — проект готов или заброшен, не ведётся: README-синк и
  weekly запись пропускают, карточка остаётся на витрине. С витринным `status` в
  frontmatter не связан. Рядом с `frozen` не ставится `path` — это тоже ошибка
  линтера.
- **Удаление записи** — вручную; папка проекта в `src/content/projects/` при
  этом остаётся и чистится тоже вручную.

### Схема для редактора

- `projects.schema.json` в корне — JSON Schema манифеста.
- Первая строка `projects.yaml`:
  `# yaml-language-server: $schema=./projects.schema.json` — подсветка опечаток
  и типов при редактировании.
- Схема проверяет форму полей; проверки диска (существование `path`, remote
  origin) делает `lint-projects.ts` (раздел 3).

## 2. Создание проекта: `c:new project <url>`

Новый режим в `scripts/new-content.ts`. Проект появляется из GitHub-ссылки;
frontmatter руками не заполняется. У созданного проекта `status: raw` и
закомментированный `# path:` — запись пока без `path` и без `frozen`, линтер
напоминает склонировать или заморозить.

### Алгоритм

1. Парсит `https://github.com/{owner}/{repo}` — иначе ошибка, ничего не пишется.
2. `GET https://api.github.com/repos/{owner}/{repo}` без авторизации;
   `GITHUB_TOKEN` из env поднимает лимит с 60 запросов/час. 404 (включая
   приватные репо) или сетевая ошибка → ошибка, ничего не пишется.
3. Заполняет поля по таблице ниже.
4. Пишет пару `index.ru.md` + `index.en.md` (en — заглушка с
   `needs_translation: true`) в `src/content/projects/<slug>/`.
5. Дописывает в `projects.yaml` запись: `slug`, `repo` и `# path: <путь>` —
   закомментирован до появления клона.
6. Печатает отчёт: что создано, что дописать руками (русское описание, subtitle,
   перевод).

### Маппинг полей из GitHub API

| Поле          | Источник                                                   |
| ------------- | ---------------------------------------------------------- |
| `slug`        | `name` репо: `focus_garden` → `focus-garden`               |
| `title`       | `name` репо (подчёркивания → дефисы)                       |
| `description` | `description` репо (about, одна строка; обычно английский) |
| `subtitle`    | `language` + топики: `rust · tauri`                        |
| `tags`        | `topics` из API; пусто — фолбэк на язык                    |
| `repo`        | исходный URL                                               |
| `homepage`    | `homepage` репо, если указан                               |
| `icon`        | словарик по языку/топикам, фолбэк `✦`                      |
| `color`       | по очереди из палитры (`coral` → `sky` → `periwinkle`)     |
| `status`      | всегда `raw`                                               |

### Повторный запуск

- Папка `src/content/projects/<slug>/` уже существует → ошибка.
- Запись с таким slug уже есть в манифесте → файлы создаются, манифест не
  дублируется.

## 3. Линтер манифеста: `lint-projects.ts` (`npm run lint:projects`)

Все проверки — ошибки (`fail`):

1. `repo` обязателен у каждой записи;
2. у записи без `frozen: true` обязателен `path`, и путь существует на диске;
3. `path` и `frozen: true` одновременно — ошибка;
4. `git -C <path> remote get-url origin` совпадает с `repo` (нормализация: с/без
   `.git`, с/без финального слэша, регистр host не важен).

Отдельный запуск — для отладки и точечных проверок. В регулярном порядке линтер
выполняется первым шагом команды `c:weekly` (раздел 7). В `verify` не входит —
один временно удалённый проект не должен блокировать весь пайплайн.

## 4. README-синк: `sync-projects.ts` (`npm run sync:projects`)

Переносит первый содержательный абзац README локального клона в файлы проекта.
Два разных уровня текста:

- **`description`** — короткая строка для витрины (карточка, соцсети). Пишется
  один раз при создании — из about GitHub, правится только руками. Скрипт её не
  трогает.
- **Тело файлов** — ручной текст плюс вставленные из README абзацы. Скрипт
  только дополняет: существующее тело никогда не перезаписывается и не
  удаляется, слияние вставок — вручную.

### Алгоритм readme-синк

1. Читает `projects.yaml`.
2. Для каждой записи с `path` (записи с `frozen` и без `path` — пропуск):
   - путь не существует → `warn`, пропуск;
   - ищет README (регистронезависимо) и определяет вариант вставки по таблице
     ниже; не найден → `warn`, пропуск;
   - извлекает первый содержательный абзац (текст после верхнего заголовка; не
     список и не код); не найден → `warn`, пропуск;
   - сравнивает README с копиями в `src/content/projects/_readmes/`; совпадает —
     ничего не делает;
   - обновляет копии в `_readmes/`;
   - вставляет абзац(ы) в конец файлов (после frontmatter) по таблице ниже;
   - пересчитывает `needs_translation` файла, получившего вставку: язык абзаца
     совпал с языком файла — снимает флаг, не совпал — ставит;
   - если `status` был `ready` — ставит `need_review`: вставка ждёт ручного
     слияния, `description` могло устареть;
   - `index.en.md` создаёт как заглушку с `needs_translation: true`, если файла
     ещё нет.

3. Печатает отчёт: создано / обновлено / `need_review` / пропущено.

### Вставка абзацев по вариантам README

| Файлы в репо                 | Куда вставляется абзац                                   |
| ---------------------------- | -------------------------------------------------------- |
| один `README.md`             | в оба файла: `index.ru.md` и `index.en.md`               |
| `README.md` + `README_ru.md` | `README_ru` → `index.ru.md`, `README.md` → `index.en.md` |
| `README.md` + `README_en.md` | `README.md` → `index.ru.md`, `README_en` → `index.en.md` |

При одиночном `README.md` язык абзаца определяется автоматически — по
большинству символов (латиница → английский, кириллица → русский): вставка идёт
в оба файла, файл другого языка получает `needs_translation: true`. При паре
соответствие задано именами файлов, язык не определяется.

Копии README хранятся в `_readmes/` рядом со слагом: `<slug>.md` для основного и
`<slug>.ru.md` / `<slug>.en.md` для парных. Изменение любого из них — триггер
вставки.

Папка `_readmes` не контент: элемент — это `*/index.*.md`, а файлы в `_readmes`
имеют другие имена, сборка их не подхватывает.

### Статусы и переходы

| Статус        | Значение                                                                                                                        |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `raw`         | проект создан, `description` сырое (из about GitHub)                                                                            |
| `ready`       | `description` переписано вручную                                                                                                |
| `need_review` | README обновился после `ready`: вставка добавлена в конец файла, `description` могло устареть — слить вставку и вернуть `ready` |

- новый проект → `raw`;
- `ready`, README изменился → `need_review`, `description` не трогается
  (сохранён ручной труд);
- `raw`, README изменился → остаётся `raw`;
- пользователь слил вставки и вычитал `description` → сам ставит `ready` (поле
  `status` в frontmatter, удобно во Frontmatter CMS);
- `need_review` на витрине — метка только в dev-режиме (как у черновиков), в
  production не выводится.

### Границы ответственности скрипта

- вставляет абзацы только в конец файла после frontmatter; существующее тело
  файлов не перезаписывает и не удаляет;
- владеет флагом `needs_translation` получивших вставку файлов и полями
  `status`, `synced_at`;
- `repo`/`homepage` переносит из манифеста при изменении (расхождения
  подсвечиваются в отчёте);
- `description`, `title`, `subtitle`, `tags`, `image`, `icon`, `color` не
  трогает.

### Git и публикация

Копии README коммитятся в репозиторий сайта:

- `git diff src/content/projects/_readmes/` — что поменялось в README проектов;
- `git diff src/content/projects/` — что поменялось в телах файлов;
- публикация изменившихся элементов: `c:publish` (раздел 6).

### Пример сгенерированного файла

`src/content/projects/now-playing/index.ru.md` — абзац из README добавлен в
конец после frontmatter:

```markdown
---
title: now-playing
subtitle: obs browser source
description: obs widget showing the currently playing track
tags:
  - html
repo: https://github.com/Ku6epXBOCTuK/now_playing
homepage: https://ku6epxboctuk.github.io/now_playing
image: images/now-playing.jpg
status: raw
synced_at: 2026-09-08
---

obs browser source widget that displays the currently playing track. ...
```

На витрину и в соцсети идёт только `description`. Парный `index.en.md` получает
тот же абзац: язык README английский — в en-файле флаг снимается, ru-файл при
английском абзаце помечается `needs_translation: true`.

## 5. Weekly-отчёты: `gen-weekly.ts` (`npm run gen:weekly`)

Полностью автоматические отчёты из git-логов; руками не создаются.

### Алгоритм weekly отчетов

1. Читает `projects.yaml`; записи с `frozen` и без `path` — пропуск.
2. Период — предыдущая неделя (понедельник–воскресенье): команда запускается в
   начале следующей недели, суббота и воскресенье уже прошли. Явно:
   `--week 2026-W36`.
3. Для каждой записи с `path`:
   - путь не существует → `warn`, пропуск;
   - `git log --since --until` — коммиты за период;
   - фильтрует шум: merge-коммиты, `[skip ci]`, bump/version-коммиты;
   - группирует по conventional-commits типам: feat / fix / docs / refactor /
     chore / прочее (cocogitto уже используется — префиксы нормализованы);
   - читает `CHANGELOG.md`, если есть, — записи за период;
   - считает статистику: коммиты, файлы, +/− строки (числа — для `excerpt`).
4. Собирает отчёт из блоков по проектам, где была активность.
5. Пишет пару в `src/content/weekly/<понедельник-отчётной-недели>/` (ISO
   `YYYY-MM-DD`): `index.ru.md` — основной язык, `index.en.md` — копия-заглушка
   с `needs_translation: true`. Body — человекочитаемый лог по проектам.
   `excerpt` — короткая сводка (проекты, коммиты, главное) для соцсетей.
6. Печатает сводку: проектов с активностью, коммитов, файл создан/обновлён.

### Вид файла

`src/content/weekly/2026-09-07/index.ru.md`:

```markdown
---
title: weekly 2026-W37
date: 2026-09-07
excerpt: 4 проекта, 23 коммита. now-playing: v1.2, git-overhooks: новый hooks api.
draft: true
---

## now-playing

- feat(overlay): blur behind panel
- fix(timer): timezone drift on resume

## git-overhooks

- feat: hooks api v2
- docs: readme examples

## итого

23 коммита в 4 проектах.
```

### Режимы

- `npm run gen:weekly` — предыдущая неделя, запись файла.
- `--week 2026-W36` — конкретная неделя (догенерировать пропущенное).
- `--check` — только отчёт в консоль, без записи.
- повторный запуск за ту же неделю → файл перезаписывается целиком (источник
  правды — git, а не файл).

### Запуск

В понедельник утром: `npm run c:weekly` (раздел 7) — линтер, синк, weekly за
прошедшую неделю. Дальше вручную: вычитка текста и
`npm run c:publish weekly @last` (раздел 6) — отправка `excerpt` в
Telegram/Discord. Пуш weekly-файла обновляет сайт. Scheduled GitHub Actions
(cron в понедельник) — этап 2.

### Архитектура под AI

Скрипт разделён на две фазы с явной границей:

- **Сбор** (детерминированная): git-логи → структура `WeeklyData` (проекты,
  коммиты по типам, статистика). Отладка: вывод в консоль/JSON.
- **Рендер** (заменяемая): `WeeklyData` → markdown-отчёт по шаблону. Позже —
  нейронка: тот же `WeeklyData` → промпт → связный текст и `excerpt`. Подмена
  рендера не требует переписывания сбора.

### Гарантии

- не ходит в сеть: только локальные git-команды и файлы;
- проекты без активности за период не попадают в отчёт;
- повторный запуск безопасен.

## 6. Публикация: `c:publish <type> @last|<slug>`

Универсальный выбор цели из командной строки вместо переменной `FILES`. Файловый
подбор через env упраздняется: prepare-логика (шаблоны `templates.json`,
`excerpt` по типам, пропуск черновиков) переезжает внутрь `scripts/publish.ts`.

### Аргументы

- `<type>` — `posts` / `articles` / `projects` / `weekly`;
- селектор цели:
  - `@last` — элемент с максимальной датой (у `posts`/`articles`/`projects` —
    `date` из frontmatter, у `weekly` — имя папки-даты);
  - `<slug>` — конкретный элемент.

### Примеры

```sh
npm run c:publish posts @last
npm run c:publish weekly @last
npm run c:publish articles my-long-read
```

### Поведение

1. Находит `index.ru.md` цели; черновик (`draft: true`) — отказ с объяснением.
2. Готовит текст по шаблону типа (как сейчас prepare-post).
3. Отправляет в Telegram/Discord через существующий механизм правок
   (`posts.yaml` хранит id сообщений — повторный запуск редактирует, а не
   дублирует).
4. Печатает отчёт: что отправлено/отредактировано, куда.

## 7. Недельный цикл: `c:weekly`

Одна команда вместо трёх ручных вызовов:

```txt
npm run c:weekly  =  lint:projects  →  sync:projects  →  gen:weekly
```

- любой шаг падает — цикл останавливается, остальные не запускаются;
- отдельные npm-скрипты остаются для точечного запуска (`lint:projects`,
  `sync:projects`, `gen:weekly`);
- `gen:weekly` без `--week` берёт предыдущую неделю — команда рассчитана на
  понедельник.

## 8. Связанные правки в существующем коде

- `frontmatter.json`: у project поле `status` (choices: `raw` / `ready` /
  `need_review`); `needs_translation` — во всех четырёх схемах.
- `scripts/lint-content.ts`: предупреждение (не ошибка) для
  `status: need_review`.
- Переименование поля `demo` → `homepage` в `src/lib/projects.ts`,
  `frontmatter.json` и карточках.
- `scripts/publish.ts`: аргументы `<type> @last|<slug>` вместо `FILES`;
  prepare-логика `prepare-post.ts` переезжает внутрь.
- `src/content/weekly/`: `.gitkeep` удалить при первом отчёте.

## 9. Этап 2 (не в текущей работе)

- содержательный перевод генерируемых типов (projects, weekly) и AI-рендер
  weekly вместо шаблона;
- `c:sync-project` — обновление витринных полей из репо по запросу;
- `gh releases` как дополнительный источник weekly;
- scheduled GitHub Actions для `c:weekly`.
